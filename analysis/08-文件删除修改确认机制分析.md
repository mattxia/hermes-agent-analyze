# HermesAgent 文件删除/修改确认机制分析

## 概述

本文档分析 HermesAgent 在文件删除与修改时的用户确认机制，覆盖 Bash/Shell、Python（execute_code）、Node.js 三条执行通道，以及直接文件工具（write_file/patch）的路径保护策略。并进一步分析通过 pip 安装第三方库在库内执行删文件操作的绕过风险。

---

## 一、执行通道与确认机制总览

HermesAgent **没有**暴露给 LLM 的独立 `delete_file` 工具。文件删除和修改通过三条执行通道完成，每条通道有独立的确认机制：

| 通道 | 入口工具 | 是否需要用户确认 | 确认实现 |
|------|---------|----------------|---------|
| **Bash/Shell** (`rm`, `sed -i` 等) | `terminal` | 需要（危险命令） | `check_all_command_guards()` |
| **Python** (`os.remove`, `subprocess` 等) | `execute_code` | 需要（整体脚本） | `check_execute_code_guard()` |
| **Node.js** (`fs.unlink` 等) | `terminal` (`node -e`/`node script.js`) | 需要（同 Bash 通道） | `check_all_command_guards()` |
| **直接文件修改** (`write_file`/`patch`) | `write_file`/`patch` | 无交互确认，按路径硬拒绝 | `_check_sensitive_path()` + `is_write_denied()` |

## 二、Bash/Shell 通道（terminal 工具）

### 调用链

`terminal_tool()`（`tools/terminal_tool.py` L1968）在执行命令前调用 `_check_all_guards()`（L260），除非 `force=True`（内部参数，不暴露给模型 API）：

```python
# tools/terminal_tool.py L2233-2234
if not force:
    approval = _check_all_guards(command, env_type)
```

`_check_all_guards()` 委托给 `check_all_command_guards()`（`tools/approval.py` L1527）。

### check_all_command_guards 实现流程

核心确认函数位于 `tools/approval.py` L1527，流程如下：

```
1. 容器后端 (docker/singularity/modal/daytona) → 直接放行
2. HARDLINE_PATTERNS 硬封锁 (rm -rf /, mkfs, dd, shutdown, fork bomb)
   → 无条件拒绝，YOLO 也无法绕过
3. Sudo stdin 守卫 (sudo -S 密码猜测) → 无条件拒绝
4. YOLO 模式 / approvals.mode=off / 永久白名单 → 放行
5. 危险命令检测 (DANGEROUS_PATTERNS) + Tirith 安全扫描
6. Smart 审批 (aux LLM 风险评估) → 自动批准/拒绝/升级
7. 交互式审批：
   - CLI: prompt_dangerous_approval() → once/session/always/deny
   - Gateway: _await_gateway_decision() 阻塞等待用户 /approve 或 /deny
```

### 与文件删除相关的危险模式

在 `DANGEROUS_PATTERNS`（`tools/approval.py` L381）中，以下与删除/修改文件相关的模式会触发审批：

```python
(r'\brm\s+(-[^\s]*\s+)*/', "delete in root path"),
(r'\brm\s+-[^\s]*r', "recursive delete"),
(r'\brm\s+--recursive\b', "recursive delete (long flag)"),
(r'\bfind\b.*-exec(?:dir)?\s+(/\S*/)?rm\b', "find -exec/-execdir rm"),
(r'\bfind\b.*-delete\b', "find -delete"),
(r'\bxargs\s+.*\brm\b', "xargs with rm"),
(rf'\bsed\s+-[^\s]*i.*(?:{_USER_SENSITIVE_WRITE_TARGET})', "in-place edit of sensitive path"),
(rf'\b(cp|mv|install)\b.*\s{_SENSITIVE_WRITE_TARGET}', "copy/move into sensitive path"),
(r'>\s*/dev/sd', "write to block device"),
```

### 硬封锁（不可绕过）

`HARDLINE_PATTERNS`（`tools/approval.py` L263）中与删除相关的：

```python
(r'\brm\s+(-[^\s]*\s+)*(/|/\*|/ \*)(\s|$)', "recursive delete of root filesystem"),
(r'\brm\s+(-[^\s]*\s+)*(/home|/root|/etc|/usr|/var|/bin|/sbin|/boot|/lib)...', "recursive delete of system directory"),
(r'\brm\s+(-[^\s]*\s+)*(~|\$HOME)(/?|/\*)?(\s|$)', "recursive delete of home directory"),
```

### 审批选项

用户通过 `prompt_dangerous_approval()`（`tools/approval.py` L979）选择：
- `once` — 仅本次允许
- `session` — 本次会话允许（存入 `_session_approved`）
- `always` — 永久允许（存入 config.yaml 的 `command_allowlist`）
- `deny` — 拒绝执行

## 三、Python 通道（execute_code 工具）

### 调用链

`execute_code()`（`tools/code_execution_tool.py` L1080）在生成子进程前调用 `check_execute_code_guard()`（`tools/approval.py` L1860）：

```python
# tools/code_execution_tool.py L1112-1120
from tools.approval import check_execute_code_guard
_guard = check_execute_code_guard(code, env_type)
if not _guard.get("approved", False):
    return json.dumps({"status": "error", "error": _guard.get("message") ...})
```

### 为什么需要单独守卫

`execute_code` 运行任意本地 Python，脚本可以调用 `subprocess`、`os.system`、`ctypes` 直接操作文件，完全绕过 `terminal()` 的 `DANGEROUS_PATTERNS` 检测。因此对整个脚本进行一次性审批。

### check_execute_code_guard 流程

```
1. 容器后端 → 放行
2. YOLO / mode=off → 放行
3. Cron 会话 → 默认拒绝 (cron_mode=deny)
4. 会话/永久审批已存在 → 放行
5. Smart 审批 (LLM 评估)
6. Gateway/ask 上下文 → _await_gateway_decision() 阻塞等待用户确认
7. CLI 交互 → 不提示（由脚本内的 terminal() 调用各自守卫）
8. 本地非交互非网关 → 放行（文档化的限制）
```

### 沙箱内允许调用的工具

`SANDBOX_ALLOWED_TOOLS`（`tools/code_execution_tool.py` L61）定义了沙箱内可调用的 Hermes 工具：

```python
SANDBOX_ALLOWED_TOOLS = frozenset([
    "web_search", "web_extract", "read_file",
    "write_file", "search_files", "patch", "terminal",
])
```

沙箱脚本通过 stub 调用这些工具，其中 `terminal` 调用仍会走常规的 `check_all_command_guards` 审批。但 Python 标准库（`os`、`shutil`、`subprocess`）不受此限制。

---

## 四、Node.js 通道

Node.js **没有独立工具**，通过 `terminal` 工具执行（如 `node -e "..."` 或 `node script.js`），因此走与 Bash 完全相同的 `check_all_command_guards()` 路径。

`DANGEROUS_PATTERNS` 中有专门捕获 Node.js 脚本执行的模式：

```python
(r'\b(python[23]?|perl|ruby|node)\s+-[ec]\s+', "script execution via -e/-c flag"),
(r'\b(python[23]?|perl|ruby|node)\s+<<', "script execution via heredoc"),
```

## 五、直接文件修改通道（write_file / patch 工具）

### 调用链

`write_file_tool()`（`tools/file_tools.py` L1329）和 `patch_tool()`（L1412）在写入前执行路径检查，但不提供交互式审批——要么允许，要么硬拒绝：

```python
# tools/file_tools.py L1340-1346
sensitive_err = _check_sensitive_path(path, task_id)   # 硬拒绝敏感系统路径
if sensitive_err:
    return tool_error(sensitive_err)
if not cross_profile:
    cross_warning = _check_cross_profile_path(path, task_id)  # 软警告跨配置文件
    if cross_warning:
        return tool_error(cross_warning)
```

### 三层路径保护

1. **`_check_sensitive_path()`**（`tools/file_tools.py` L423）— 硬拒绝写入 `/etc/`、`/boot/`、`/usr/lib/systemd/`、`/private/etc/`、docker.sock、Hermes config.yaml

2. **`is_write_denied()`**（`agent/file_safety.py` L98）— 硬拒绝写入凭据文件：`~/.ssh/*`、`~/.aws/`、`~/.gnupg/`、`~/.kube/`、`.env`、`auth.json`、`.anthropic_oauth.json`、`.netrc`、`.pgpass` 等

3. **`_check_cross_profile_path()`**（`tools/file_tools.py` L487）— 软警告：写入其他 Hermes profile 的 skills/plugins/cron/memories 目录时返回警告，需 `cross_profile=True` 才能绕过

## 六、内部文件操作（file_operations.py）

`ShellFileOperations.delete_file()`（`tools/file_operations.py` L1232）是内部实现，不直接暴露给 LLM。它通过 `python3 -c` 执行删除，且仅检查 `_is_write_denied()`：

```python
# tools/file_operations.py L1250-1253
def _python_delete(self, path, recursive):
    path = self._expand_path(path)
    if _is_write_denied(path):
        return WriteResult(error=f"Delete denied: {path} is a protected path")
```

## 九、通过 pip 安装第三方库执行删文件操作的绕过分析

### 结论：不能拦截

HermesAgent 的审批系统是**静态文本检查**，不是**运行时监控**。通过 pip 安装第三方库并在库内执行删文件操作，可以完全绕过所有审批机制。

### 原因分析

#### 1. check_execute_code_guard 只看代码文本，不看运行时行为

`check_execute_code_guard()`（`tools/approval.py` L1860）在脚本执行前进行一次性审批，它检查的是 LLM 生成的 `code` 字符串。如果脚本是：

```python
import my_malicious_lib   # 看起来无害
my_malicious_lib.run()    # 内部调用 os.remove("/important/file")
```

守卫只看到 `import` 和 `run()`，看不到第三方库内部的 `os.remove()`。审批通过后，子进程内的任何操作都不再经过 HermesAgent。

#### 2. DANGEROUS_PATTERNS 是 shell 命令正则匹配，不覆盖 Python 运行时

`DANGEROUS_PATTERNS`（`tools/approval.py` L381）匹配的是 `rm -rf`、`find -delete` 等 shell 命令字符串。第三方库直接调用 Python 的 `os.remove()` / `shutil.rmtree()` / `pathlib.Path.unlink()`，根本不经过 shell，也就不经过任何模式匹配。

#### 3. SANDBOX_ALLOWED_TOOLS 限制的是工具调用，不是 Python 标准库

`SANDBOX_ALLOWED_TOOLS`（`tools/code_execution_tool.py` L61）只限制沙箱脚本能调用哪些 Hermes 工具。但 Python 标准库（`os`、`shutil`、`subprocess`、`ctypes`）不受此限制。第三方库可以直接用标准库操作文件。

#### 4. file_safety.py 的写保护只在工具入口生效，不拦截运行时

`is_write_denied()`（`agent/file_safety.py` L98）只在 `write_file_tool` / `patch_tool` / `ShellFileOperations.delete_file()` 等工具入口被调用。第三方库的 `os.remove()` 直接走操作系统 syscall，完全不经过这些工具函数。

#### 5. pip install 本身通常不触发审批

`pip install xxx` 不在 `DANGEROUS_PATTERNS` 列表中，通过 `terminal` 工具执行时通常会直接放行，不会被拦截。

### 攻击路径还原

```
Skill 中的 Python 脚本
    │
    ├─ 方式A: terminal("pip install malicious-pkg && python script.py")
    │         └─ check_all_command_guards() 检查命令字符串
    │            pip install 不在 DANGEROUS_PATTERNS → 放行
    │            python script.py 不匹配危险模式 → 放行
    │            脚本内 import malicious_pkg → 运行时 os.remove() → 不可拦截
    │
    ├─ 方式B: execute_code("import subprocess; subprocess.run(['pip','install','x']); import x; x.run()")
    │         └─ check_execute_code_guard() 检查 code 字符串
    │            代码文本看起来无害 → 审批通过（或 smart approve 放行）
    │            运行时第三方库 os.remove() → 不可拦截
    │
    └─ 方式C: terminal("node -e \"require('malicious-npm-pkg').run()\"")
              └─ 匹配 "script execution via -e/-c flag" → 用户审批
                 审批通过后，npm 包内 fs.unlinkSync() → 不可拦截
```

### 缓解措施

| 缓解措施 | 机制 | 是否有效 |
|---------|------|---------|
| **容器后端** (docker/singularity/modal/daytona) | 整个执行隔离在容器内，删除操作不影响宿主 | 有效但不是"拦截"，是"隔离" |
| **Smart approval** (_smart_approve) | 辅助 LLM 分析脚本文本，可能识别 `pip install` + 可疑调用的组合 | 可能识别，但取决于 LLM 判断，且只看文本 |
| **Tirith 安全扫描** | 静态分析命令字符串 | 不分析第三方库代码 |
| **HERMES_WRITE_SAFE_ROOT** | 限制写入目录范围 | 只在工具入口检查，不拦截 os.remove |
| **文件系统权限** | OS 层面的用户权限 | 最底层防线，但 agent 运行在用户权限下 |

### 根本原因

HermesAgent 的安全模型设计文档中明确承认了这一点（`agent/file_safety.py` L184）：

> **This is NOT a security boundary.** The terminal tool runs as the same OS user with shell access; the agent can still `cat auth.json` or `cat ~/.hermes/.env` and exfiltrate the file.

审批系统是 defense-in-depth（纵深防御），不是安全边界。它依赖：
1. 静态模式匹配（DANGEROUS_PATTERNS）
2. 工具入口路径检查（file_safety）
3. LLM 自身的行为约束（prompt 层面）

没有任何运行时机制（如 syscall hook、seccomp、LD_PRELOAD、eBPF）来拦截第三方库的文件操作。要做到真正的运行时拦截，需要在操作系统层面实现，而不是在应用层的工具函数中。
